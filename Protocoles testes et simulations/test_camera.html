Apprendre le mode snapshot

TRÈS IMPORTANT POUR LE SCANNER

4.1 — Pourquoi

Le scanner sera d’abord exploité en stratégie Stop-and-Scan. Il est donc plus utile de savoir demander une image au moment choisi que de dépendre uniquement d’un flux continu.

4.2 — S’appuyer sur le middleware caméra ST

Les applications récentes STM32N6 de ST utilisent une couche Camera Middleware avec une API de type :

CMW_CAMERA_Start(
    DCMIPP_PIPE2,
    destination_buffer,
    CAMERA_MODE_SNAPSHOT
);

Le TP doit donc te faire identifier dans un exemple ST récent :

  • CMW_CAMERA_Init(...) ou équivalent ;
  • CMW_CAMERA_Start(...) ;
  • la configuration CAMERA_MODE_SNAPSHOT ;
  • le callback/flag indiquant qu’une frame est terminée.

4.3 — Test recherché

  1. Programme arrêté ou en attente.
  2. Déclenche une capture snapshot.
  3. Attends l’indication de fin de frame.
  4. Incrémente g_snapshot_count.
  5. Relance une seconde capture.

Résultat attendu : g_snapshot_count augmente d’une unité par image demandée, et non en continu.

Créer un type CameraFrame réutilisable

CODE À CONSERVER

5.1 — Créer camera_types.h

Dans le projet de TP :

Core/Inc/camera_types.h

Contenu de départ :

#ifndef CAMERA_TYPES_H
#define CAMERA_TYPES_H

#include <stdint.h>

typedef enum
{
    CAMERA_PIXEL_FORMAT_UNKNOWN = 0,
    CAMERA_PIXEL_FORMAT_RGB565,
    CAMERA_PIXEL_FORMAT_RGB888,
    CAMERA_PIXEL_FORMAT_RAW10
} CameraPixelFormat;

typedef struct
{
    uint32_t frame_id;
    uint32_t timestamp_ms;

    uint16_t width;
    uint16_t height;

    CameraPixelFormat format;

    uint8_t *data;
    uint32_t data_size_bytes;

} CameraFrame;

#endif

5.2 — Principe mémoire

Ne mets pas une image complète sous forme de tableau directement dans CameraFrame. La structure doit contenir un pointeur vers le framebuffer, sinon chaque copie de structure dupliquerait potentiellement une énorme quantité de données.

5.3 — Test

Crée une instance globale :

static CameraFrame g_camera_frame;

Remplis manuellement width, height, data, frame_id et timestamp_ms, puis observe-les dans le debugger.

Créer CameraSource : l’API que l’on réutilisera dans le scanner

ARCHITECTURE CLÉ

6.1 — Créer les fichiers

6.2 — API cible

#ifndef CAMERA_SOURCE_H
#define CAMERA_SOURCE_H

#include <stdbool.h>
#include "camera_types.h"

bool CameraSource_Init(void);

6.3 — Règle de conception

main.c ne doit plus connaître directement :

  • IMX335_Probe() ;
  • les détails DCMIPP ;
  • les détails de l’ISP ;
  • l’adresse matérielle du framebuffer.

Ces détails doivent rester derrière CameraSource_*.

6.4 — Test de non-régression

Après migration, la capture doit continuer à fonctionner exactement comme avant.

Phase validée si : main.c peut demander une image via CameraSource_Capture() sans appeler directement le driver IMX335 ou HAL DCMIPP.

Ajouter frame_id et timestamp au bon moment

FUTURE SYNCHRONISATION

7.1 — Quand timestamp-er ?

Pour le scanner, il faut distinguer :

  • instant où la capture est demandée ;
  • instant où la frame est terminée.

V1 : stocke au minimum un timestamp cohérent au déclenchement ou à la réception de la frame, puis documente précisément lequel tu utilises.

7.2 — Dans CameraSource_Capture()

À chaque nouvelle capture :

frame->frame_id++;
frame->timestamp_ms = HAL_GetTick();

À terme, le compteur doit appartenir au module caméra plutôt qu’à l’appelant.

7.3 — Test

Capture 5 images successives et vérifie :

frame_id : 1, 2, 3, 4, 5
timestamp_ms : valeurs croissantes

Préparer les deux usages futurs de l’image

VISUALISATION + IA

9.1 — Pourquoi deux pipelines

Les exemples ST récents exploitent plusieurs pipes DCMIPP. Pour ton futur scanner, le principe sera utile :

Pipe A : image d'affichage / archive
Pipe B : image redimensionnée pour IA

9.2 — Ne pas intégrer YOLO maintenant

Le but du TP est seulement de savoir produire :

  • une frame « principale » ;
  • une frame plus petite destinée plus tard à l’IA, par exemple autour de 320×320 selon le modèle choisi.

9.3 — Test

Vérifie que les deux destinations mémoire sont distinctes et que leur taille correspond à leur résolution/format.

Préparer la synchronisation caméra–LiDAR

POUR LE SYSTÈME COMPLET

10.1 — API visée

CameraSource_Capture(&camera_frame);
LidarSource_GetFrame(&lidar_frame);

Les deux frames auront :

camera_frame.timestamp_ms
lidar_frame.timestamp_ms

10.2 — V1 Stop-and-Scan

scanner immobile
→ déclencher caméra
→ obtenir CameraFrame
→ déclencher / lire LiDAR
→ obtenir LidarFrame
→ calculer delta_t
→ accepter la paire si delta_t est suffisamment faible

10.3 — Structure de paire future

typedef struct
{
    CameraFrame camera;
    LidarFrame lidar;
    uint32_t pair_id;
    uint32_t delta_t_ms;
} SensorPair;
L’objectif du TP caméra est que, le jour de l’intégration, on n’ait pas à réécrire l’acquisition caméra : on devra seulement connecter CameraSource au coordinateur multi-capteurs.
